==================================================================
سوق الرافدين — توثيق النسخ الاحتياطي والاسترجاع
(Rafidain Market — Backup & Restore)
==================================================================

1) أين توجد النسخ الاحتياطية؟
--------------------------------------------------------
المجلد الافتراضي:  server/data/backups/

ويُشتق من مجلد قاعدة البيانات نفسها (BACKUP_DIR = مسار قاعدة البيانات + "backups").
يمكن تغييره في .env عبر:  BACKUP_DIR=./data/backups

ماذا يوجد داخل المجلد؟ كل ساعة يتولد ملفان بنفس الطابع الزمني:
  app-2026-08-09T22-13-59.db      لقطة قاعدة البيانات (VACUUM INTO)
  app-2026-08-09T22-13-59.zip     الحزمة الكاملة = app.db + مجلد الصور uploads

الاسم يتبع الصيغة:  app-YYYY-MM-DDTHH-MM-SS.db / .zip

--------------------------------------------------------
2) متى وكيف تُنشأ؟
--------------------------------------------------------
- تلقائياً كل ساعة داخل الخادم (setInterval في server/src/index.js).
- تعمل على قاعدة WAL: تُدمج WAL أولاً ثم تُأخذ لقطة ذرية متسقة.
- الحزمة الكاملة (zip) تُنشأ بجانب كل لقطة، وتضم:
    * app.db          قاعدة البيانات كاملة
    * uploads/...     جميع صور النظام في server/data/uploads
- الاحتفاظ: آخر 7 نسخ فقط (BACKUP_KEEP) وتحذف الأقدم تلقائياً (تُطبق على db و zip).
- سقف حجم الحزمة: BACKUP_BUNDLE_MAX_BYTES (افتراضي 1 جيجابايت). إذا تجاوزت
  الصور هذا السقف تُنبّه وتُدفع النسخة المحلية للقاعدة فقط، أو تُدفع قاعدة .db خارجياً.

--------------------------------------------------------
3) الدفع خارج الموقع (اختياري)
--------------------------------------------------------
عيّن في .env الأمر الذي يُنفَّذ بعد كل نسخة محلية، ويُستبدل فيه {file} بمسار النسخة:

  # rclone إلى سحابة:
  OFFSITE_BACKUP_CMD=rclone copy {file} remote:rafidain-backups

  # scp إلى سيرفر آخر:
  OFFSITE_BACKUP_CMD=scp -i ~/.ssh/id_backup {file} backup@backup.example:/srv/rafidain/

ملاحظات:
- تُدفع الحزمة الكاملة (zip) إن وُجدت، وإلا قاعدة .db.
- يُنفَّذ بلا حجب حلقة الأحداث (لا يبطئ الخادم).
- فشل الدفع يُسجَّل فقط ولا يكسر النسخ المحلية.
- يُنصح بنسخ server/data/vapid.json مع النسخ حتى لا تنقطع إشعارات Web Push
  عند إعادة تثبيت الخادم.

--------------------------------------------------------
4) الاسترجاع الآلي (المُوصى به)
--------------------------------------------------------
من مجلد server:

  # 1) أوقف الخادم
  pm2 stop rafidain-server

  # 2) استعد أحدث نسخة (يطلب تأكيداً تفاعلياً)
  npm run restore

  # أو لنسخة محددة:
  npm run restore -- --file ../server/data/backups/app-2026-08-09T22-13-59.zip
  npm run restore -- --file app-2026-08-09T22-13-59.db --yes

  # 3) أعد تشغيل الخادم (الترحيلات تُطبَّق تلقائياً عند الإقلاع)
  pm2 start rafidain-server

مفاتيح السكربت (server/scripts/restore.js):
  --file <path>   تحديد نسخة معينة (zip كامل أو db فقط)
                  بدونها يختار أحدث نسخة تلقائياً (يُفضّل الحزمة الكاملة)
  --yes           يتجاوز سؤال التأكيد (مناسب للتشغيل الآلي)
  --keep          لا ينشئ نسخة أمان من الحالة الحالية قبل الاستعادة

ماذا يفعل السكربت بالترتيب؟
  1) يحفظ نسخة أمان من قاعدة البيانات الحالية باسم app.db.pre-restore-<stamp>
     (تحسباً من أي خطأ، ولا تُحذف تلقائياً).
  2) يعالج النسخة: يستخرج الحزمة zip كاملة (app.db + uploads)، أو ينسخ .db وحدها.
  3) يتحقق من سلامة القاعدة بـ PRAGMA integrity_check — أي نسخة تالفة ترفض دون تغيير أي ملف.
  4) بعد التأكيد: يستبدل قاعدة البيانات ويحذف ملفات WAL/SHM القديمة (app.db-wal، app.db-shm)
     لأنها قد تحمل بيانات غير متسقة.
  5) إن كانت النسخة حزمة كاملة: يستبدل مجلد الصور uploads بالكامل.
     (حزمة بلا مجلد صور = تُترك الصور الحالية كما هي.)
  6) تحقق نهائي من القاعدة بعد الاستعادة، ثم يخبرك بالنجاح.
- أمان المسارات: أي إدخال في الأرشيف باسم متجاوز (.. أو مسار مطلق) يُطبع إلى اسم
  آمن داخل الوجهة ولا يمكنه الكتابة خارج مجلد الاستعادة.

--------------------------------------------------------
5) الاسترجاع اليدوي (بديل)
--------------------------------------------------------
  pm2 stop rafidain-server
  mv server/data/app.db server/data/app.db.broken
  cp server/data/backups/app-<stamp>.db server/data/app.db
  pm2 start rafidain-server

(لا يغطي هذا مجلد الصور — للاستعادة الكاملة استعمل npm run restore.)

--------------------------------------------------------
6) اختبار الاستعادة
--------------------------------------------------------
- اختبارات تلقائية في server/test/maintenance.test.js تغطي:
  * إنشاء النسخة من قاعدة WAL وفتحها سليماً
  * integrity_check + احتواء الجداول والسجلات
  * محاكاة الاستعادة لمسار جديد
  * الاحتفاظ بآخر 7 نسخ
  * الدفع خارج الموقع (حل {file} والنسخ الفعلي)
  * الحزمة الكاملة zip (تشمل app.db والصور، واستخراجها والتحقق منها)
  * أمان أرشيف ضار (أسماء متجاوزة لا تخرج عن الوجهة)
- التشغيل:  cd server && npm test
