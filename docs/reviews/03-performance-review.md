# تقرير مراجعة الأداء

> التاريخ: 2026-08-09 — الحالة: ✅ **مقبول للحجم المستهدف** (مع قيد معماري واحد موثّق)

## 1. الخلاصة التنفيذية

أُغلقت أغلب بنود الأداء التنبؤية (ترقيم، N+1، فهارس، بث CSV، إعادة محاولة BUSY). القيد الوحيد المتبقي هو `node:sqlite` المتزامن (`DatabaseSync`) الذي يحجب حلقة الأحداث — مقصود ومقبول لحجم لوحات داخلية + حركة محافظة، وله خارطة معالجة موثّقة (Worker Thread ثم Postgres).

## 2. جدول الحالة

| # | البند | المستوى | الحالة | التفاصيل |
|---|---|---|---|---|
| S1 | `DatabaseSync` يحجب حلقة الأحداث | 🔴 | **مفتوح (قيد معماري)** | كل استعلام متزامن؛ سقف throughput عند التزامن؛ معالجة: Worker Thread بنفس واجهة `db/index.js` أو Postgres |
| S2 | bcrypt متزامن | 🟠 | ✅ مغلق | `password.js` يستخدم `hash/compare` غير المتزامنين في كل المسارات الحساسة |
| S3 | قوائم بلا حدود | 🟠 | ✅ مغلق | `paginate` إلزامي دائماً (افتراضي 50 / سقف 100) مع `meta{total,page,limit,pages}` على كل القوائم |
| S4 | استعلامات N+1 | 🟠 | ✅ مغلق | `decorateOrders` (دفعة `IN`)، وكلاء `LEFT JOIN` بتجميع واحد، خدمات `LEFT JOIN` مع `GROUP BY` |
| S5 | فهارس مفقودة | 🟡 | ✅ مغلق | هجرتا 004 (7 فهارس) و005 (3 فهارس) |

## 3. التفاصيل

### 3.1 القيد المعماري S1 (يستوجب الوعي)
- كل `get/all/run/transaction` يُنفَّذ متزامناً فيجمّد حلقة الأحداث؛ عملية ثقيلة واحدة ترفع زمن استجابة كل الطلبات.
- **التقييم:** مقبول تماماً الآن؛ يتحول إلى عنق زجاجة فقط عند حمل عام كبير.
- **الخطة:** المرحلة ب = عزل DB في Worker عبر نفس الواجهة (تغيير محصور في `db/index.js`)؛ المرحلة ج = Postgres بطبقة بديلة بنفس الواجهة.

### 3.2 معالجات محسّنة
- **البث في تصدير CSV:** `GET /orders/export` يكتب بشرائح 500 (لا بناء ملف كامل بالذاكرة) بحد 10,000 صف.
- **إعادة محاولة SQLITE_BUSY:** 3 محاولات بفاصل تصاعدي في كل عمليات DB، وتحويل الباقي إلى `503` (بدل 500).
- **WAL + نسخ احتياطي:** `VACUUM INTO` ذري كل ساعة مع `wal_checkpoint(TRUNCATE)` قبلها، وإبقاء 7 نسخ.
- **تدوير السجلات:** `activity_log` 90 يوم، ملفات السجل 10MB × 3، ومفاتيح Idempotency 7 أيام.
- **رؤوس الكاش (nginx):** مضبوطة في `deploy/` بحيث يصل التحديث للزبائن تلقائياً مع كاش فعّال للأصول الثابتة.

### 3.3 أداء الواجهات
- تطبيق الزبون مقسّم شيفرة (تحميل كسول للمسارات) — أول لود أصغر.
- عدّادات الجرس (لوحات/جوال) تُحدَّث دورياً (20–30 ثانية) لا بلحظي — تجنّب إشغال نقاط البث.
- حدود معدل عامة للكتابة تمنع إساءة الاستخدام التي تضر بالأداء والاستقرار.

## 4. اختبار الأداء

- لا يوجد اختبار تحميل آلي (load test) حالي. الاختبارات الموجودة تغطي الاستقرار (503 عند BUSY، الاقتطاع، التدوير) لا القدرة.
- **توصية:** عند الاقتراب من الحمل العام، تنفيذ فحص تحميل بسيط (مثل `k6`/`autocannon`) على مسارات الطلبات والكتالوج لتحديد عتبة S1 بدقة.

## 5. التوصيات (حسب الأولوية)

1. **عند الحاجة فقط:** عزل DB في Worker Thread (خطوة واحدة قابلة للتراجع، توافق كامل مع الواجهة الحالية).
2. **قريباً:** اختبار تحميل بسيط لتثبيت عتبات S1 أرقامياً.
3. **لاحقاً:** تجميعات مادية (Materialized) للتقارير (dashboard/commissions) عند نمو البيانات، أو Postgres.
