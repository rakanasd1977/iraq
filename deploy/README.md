# النشر والإنتاج (HTTPS)

خطة النشر لمنصة سوق الرافدين على سيرفر حقيقي (Ubuntu/Debian مقترح). الإشعارات
Web Push في متصفحات الهاتف غير المثبتة كـ PWA **تتطلب HTTPS**، وكذلك أي استقبال
حقيقي لدفع إلكتروني مستقبلاً.

## متطلبات التشغيل على السيرفر

- **نظام التشغيل:** Ubuntu 22.04/24.04 LTS أو Debian 12 (أي توزيعة تدعم Node.js 23+). يُفضّل توزيعة LTS محدّثة ودعم `systemd`.
- **Node.js:** إصدار **23+** (النظام يستخدم وحدة `node:sqlite` المدمجة، فلا حاجة لتثبيت قاعدة بيانات خارجية). ثبّت عبر [NodeSource](https://github.com/nodesource/distributions).
- **npm:** الإصدار الملائم لـ Node 23.
- **الذاكرة (RAM):** 1 جيجابايت كحد أدنى، **يُوصى بـ 2 جيجابايت فأعلى**. الخادم يُشغّل عمليات cluster بعدد `CLUSTER_WORKERS` (افتراضي = عدد الأنوية، بسقف 4)، ويستخدم ذاكرة مشتركة (`SharedArrayBuffer`).
- **القرص:** 20 جيجابايت فأعلى. تشمل: قاعدة WAL + **نسخ احتياطية تلقائية كل ساعة** (`server/data/backups/`) + الصور المرفوعة (`server/data/uploads/`). راقب نمو مجلد الصور خصوصاً مع `OFFSITE_BACKUP_CMD`.
- **عكس الوكيل:** nginx (أو Traefik) مع **شهادة TLS** (Let's Encrypt) — **HTTPS إلزامي** (Web Push والإشعارات تتطلبه، وأي دفع مستقبلي).
- **مدير العمليات:** [PM2](https://pm2.keymetrics.io/) لإعادة التشغيل التلقائي والإقلاع مع النظام (`pm2 startup`/`pm2 save`).
- **الصلاحيات:** المستخدم الذي يشغّل الخادم يحتاج صلاحية **كتابة على `server/data/` فقط** (قاعدة البيانات + النسخ + الصور + `vapid.json`). لا تشغّله كـ root.
- **جدار الحماية:** اسمح بـ `80/443` من الخارج فقط؛ المنفذ `4001` داخلي خلف nginx ولا يُعرّض للإنترنت.
- **خروج للإنترنت (اختياري):** للسماح بـ `certbot` وبدفع النسخ الاحتياطية الخارجية (`OFFSITE_BACKUP_CMD` مثل rclone/scp).
- **المنطقة الزمنية:** اضبط السيرفر على **UTC** (`timedatectl set-timezone UTC`) لأن فلاتر التقارير/الإشعارات تعتمد على تواريخ محلية ثابتة.

> لا تُشغّل الخادم مباشرة على المنفذ 4001 للعموم؛ اجعله دائماً خلف nginx (HTTPS) وPM2.

## البنية الهدف

```
الإنترنت --HTTPS--> nginx :443  --/api-->  node (خادم API على 4001)
                        |--/-->  واجهة الزبون (customer-mobile/dist)
                        |--/-->  لوحة المسؤول (مجال فرعي)
                        |--/-->  لوحة المزوّد (مجال فرعي)
                        |--/-->  لوحة الوكيل (مجال فرعي)
```

الواجهات بُنيت بمسار API نسبي (`/api`)، لذلك كل لوحة تُقدَّم من أصل مستقل (مجال
فرعي) — كما المنافذ المحلية تماماً.

## الخطوات

1. **تثبيت التبعيات وبناء الواجهات**
   ```bash
   cd server && npm install --omit=dev
   cd ../customer-mobile && npm install && npm run build
   cd ../admin-panel    && npm install && npm run build
   cd ../provider-panel && npm install && npm run build
   cd ../agent-panel    && npm install && npm run build
   ```
   انقل مجلدات `dist` إلى `/var/www/rafidain/<name>/`.

2. **إعداد البيئة**
   ```bash
   cd server && cp .env.example .env
   # عدّل JWT_SECRET (openssl rand -hex 32)، DB_PATH، والمجالات في CORS_ORIGINS
   ```

3. **تشغيل الخادم** — عبر PM2:
   ```bash
   pm2 start deploy/ecosystem.config.js --env production && pm2 save && pm2 startup
   ```

4. **عكس الوكيل والشهادة** — انسخ `deploy/nginx.conf.example` وعدّل أسماء المجالات،
   ثم:
   ```bash
   certbot --nginx -d rafidain.example -d admin.rafidain.example -d provider.rafidain.example -d agent.rafidain.example
   nginx -t && systemctl reload nginx
   ```
   كرر `server {}` في nginx لكل مجال فرعي (كل واجهة جذرها الخاص).

5. **TRUST_PROXY:** فعّل `TRUST_PROXY=1` في `.env` لأن nginx هو الذي يمرر
   `X-Forwarded-For` (حدود معدل الطلبات تعتمد عليه).

6. **بيانات أولية:** شغّل seed تهيئة البيانات الأولية في أول تشغيل فقط:
   ```bash
   cd server && SEED_ALLOW=1 npm start
   ```
   بعد ذلك أعد تشغيله بدون `SEED_ALLOW` كي لا يُعاد إدراج بيانات التجربة عند كل
   إقلاع (الخادم يرفض الـ seed في `production` إلا بتفويض صريح).

## النسخ الاحتياطية التلقائية والاستعادة

الخادم ينشئ نسخة احتياطية تلقائياً **كل ساعة** عبر `VACUUM INTO` في
`server/data/backups/` (قابلة للضبط عبر `DB_PATH` و`BACKUP_DIR`):

- تلقائي — يعمل داخل الخادم عبر `setInterval` بدون تدخل خارجي
- يُبقي آخر 7 نسخ (`BACKUP_KEEP`) ويحذف الأقدم
- يعمل على قاعدة WAL: يدمج WAL أولاً ثم يأخذ لقطة ذرية
- **حزمة كاملة:** مع كل نسخة يُنشأ أيضاً `app-<stamp>.zip` يضم قاعدة البيانات
  **ومجلد الصور** `server/data/uploads/` (حتى تصبح الاستعادة كاملة على خادم جديد)،
  بسقف حجم `BACKUP_BUNDLE_MAX_BYTES` (افتراضي 1 جيجا) — إذا تجاوزته الصور تُنبَّه
  وتُدفع النسخة المحلية للقاعدة فقط.
- يوجد اختبار تلقائي للاستعادة في `server/test/maintenance.test.js`

**دفع خارجي (اختياري — يُغلق المخاطرة R6/R13):** عيّن `OFFSITE_BACKUP_CMD` في `.env`
لدفع كل نسخة إلى موقع آخر (سحاب/قرص مثبّت/سيرفر آخر) عبر rclone/scp/cp، فيُستبدل
`{file}` بمسار النسخة — تُدفع الحزمة الكاملة (zip) إن وُجدت، وإلا قاعدة .db:

```bash
# سحاب (rclone): الدفع للنسخة الكاملة
OFFSITE_BACKUP_CMD=rclone copy {file} remote:rafidain-backups

# سيرفر آخر (scp)
OFFSITE_BACKUP_CMD=scp -i ~/.ssh/id_backup {file} backup@backup.example:/srv/rafidain/
```

يُنفَّذ بلا حجب حلقة الأحداث، والفشل يُسجَّل فقط ولا يكسر النسخ المحلي. يُنصح
بنسخ `data/vapid.json` مع النسخ أيضاً (راجع قائمة الفحص أدناه).

**الاستعادة الآلية (موصى بها):** سكربت `restore` يعالج الحزمة الكاملة (قاعدة
+ صور) وقاعدة .db وحدها، ويختار أحدث نسخة إن لم يُحدَّد ملف، وينشئ نسخة أمان من
الحالة الحالية قبل الاستعادة، ويتحقق من سلامة القاعدة (`integrity_check`) قبل
وبعد، ويرفض الأرشفة المتجاوزة للمسار:

```bash
pm2 stop rafidain-server
cd server
npm run restore -- --yes              # أحدث نسخة تلقائياً
# أو لنسخة محددة: npm run restore -- --file server/data/backups/app-<stamp>.zip --yes
pm2 start rafidain-server             # الترحيلات تُطبَّق تلقائياً
```

بدون `--yes` يطلب السكربت تأكيداً تفاعلياً. النسخة السابقة تُحفظ باسم
`app.db.pre-restore-<stamp>` تحسباً. الاستعادة اليدوية عند الحاجة:
```bash
pm2 stop rafidain-server
mv server/data/app.db server/data/app.db.broken
cp server/data/backups/app-<stamp>.db server/data/app.db
pm2 start rafidain-server   # الترحيلات تُطبَّق تلقائياً
```

## قبل الإطلاق (قائمة فحص)

- [ ] `JWT_SECRET` عشوائي طويل في `.env` (الإقلاع يفشل بدونه في `production`).
- [ ] `TOTP_ENC_KEY` عشوائي طويل في `.env` (الإقلاع يفشل بدونه في `production` — يشفّر أسرار 2FA عند الراحة). ولّده بـ `openssl rand -hex 32`.
      إن كانت لديك أسرار 2FA مشفّرة سابقاً بالمفتاح الثابت القديم (نسخة تطوير)، اضبطه مؤقتاً على تلك القيمة ثم بدّل المستخدمين لإعادة تفعيل 2FA للتدوير.
- [ ] ربط الأرقام/الآيبانات الفعلية من لوحة المسؤول ← الإعدادات ← حسابات الشحن.
- [ ] بيانات أولية واقعية: شغّل الـ seed بـ `SEED_ALLOW=1` ثم أعد الإقلاع بدونه،
      ومحو بيانات الاختبار الزائدة.
- [ ] الإشعارات: بعد الإقلاع الأول يتولد `server/data/vapid.json` — احفظه مع النسخ
      الاحتياطية كي لا تنقطع الإشعارات عند إعادة تثبيت الخادم.
- [ ] سجلات: تحقق من `/var/log/rafidain/*.log` و`LOG_ROTATE_BYTES`.
- [ ] حد معدل الطلبات: فعّل `RATE_LIMIT_MAX=10` في الإنتاج (احمِ مسارات الدخول).
- [ ] افحص هجمات: تصفح الموقع كزائر ثم كمسؤول، وتأكد من HTTPS في كل الصفحات.
- [ ] تحقق من النسخ الاحتياطية: تأكد من ظهور ملفات (`.db` وحزمة `.zip`) في
      `server/data/backups/` بعد الساعة الأولى من التشغيل.
- [ ] بعد كل إصدار جديد انسخ `dist` الجديد إلى `/var/www/...` — وأخبر المستخدمين
      بتحديث الصفحة (رؤوس الكاش في `nginx.conf.example` تجعل التحديث تلقائياً بعد
      أول زيارة، وإذا ظهرت نسخة قديمة جداً فالمتصفح خزّن `index.html` قبل تطبيق
      الإعداد — نفّذ تحديثاً صعباً Ctrl+F5 أو امسح بيانات الموقع).

## الأمان في الإنتاج (مهم)

التحصين مُطبَّق في الكود (رؤوس أمان، CSP صارم في بناء الواجهات، تثبيت خوارزمية
JWT، تعقيم أجسام الطلبات من `__proto__`، وحدود معدل الطلبات). في الإنتاج تأكد من:

- **رؤوس nginx:** استخدم `deploy/nginx.conf.example` كما هو — يضيف `X-Frame-Options:
  DENY` (حماية التأطير الفعلية للواجهات لأن `frame-ancestors` لا يعمل عبر meta)،
  `Content-Security-Policy` صارم، `X-Content-Type-Options: nosniff`،
  `Referrer-Policy: no-referrer`، `Permissions-Policy`، و`Strict-Transport-Security`.
- **`X-Frame-Options` إلزامي** على كل واجهة — لا تعتمد على meta CSP للتأطير.
- **CSP:** `connect-src 'self'` و`script-src 'self'` يبطلان هجمات XSS واستخراج
  البيانات (الخادم API لا يرسل إلا JSON، والتطبيق لا يحمل موارد خارجية سوى صور
  https اختيارية). لا تُرخِ `script-src` إلا عند الحاجة وبوعي.
- **TLS:** بروتوكولات TLSv1.2/TLSv1.3 فقط (كما في المثال)، وHTTPS إلزامي
  (Web Push والإشعارات تتطلب HTTPS).
- **RATE_LIMIT_MAX=10** و`TRUST_PROXY=1` (خلف nginx) كي تعمل حدود معدل الطلبات
  على عناوين IP الحقيقية لا المزوّرة.
- **فحص أمني سريع** بعد النشر: تأكد من ظهور رؤوس الأمان في أدوات المطوّر على
  صفحة الواجهة ومسار `/api`، ومن أن التوكنات لا تظهر في السجلات/الردود.

## متغيرات البيئة الكاملة

راجع `server/.env.example` — يغطي المنفذ، `JWT_SECRET`، `TOTP_ENC_KEY` (مطلوب
في الإنتاج)، قاعدة البيانات (`DB_PATH`/`BACKUP_DIR`)، CORS، `TRUST_PROXY`
(مفعّل افتراضياً في الإنتاج)، حدود الطلبات (`RATE_LIMIT_MAX`/`WRITE_RATE_LIMIT_MAX`)،
VAPID (توليد تلقائي في `data/vapid.json` أو متغيرات صريحة)، ومقاس تدوير
السجلات (`LOG_ROTATE_BYTES`).

## إصلاحات وتحصينات ما قبل الإنتاج (هذه النسخة)

أُجريت قبل الإطلاق سلسلة إصلاحات وتحصينات على الكود لتجهيزه للإنتاج:

- **منع سباق فقدان التحديث (lost-update):** المعاملات الآن تبدأ بـ `BEGIN IMMEDIATE`
  فتُؤخذ قفل الكتابة فوراً، ما يمنع تداخل عمليات الرصيد/المخزون/العدّاد عبر عمليات
  cluster المتعددة ويضمن صحة الأرصدة المالية.
- **تعافٍ من تعطّل عامل قاعدة البيانات:** أُصلح تطابق مفاتيح الطلبات المعلّقة
  (`inflight`) مع العامل الصحيح، فعند خروج/خطأ عامل الـ DB تُرفض الطلبات المعلّقة
  بدل تجمّد العملية بالكامل (توقف صامت).
- **إشعارات المسؤول الدورية:** كان عمود `name_ar` خاطئاً في استعلام السحوبات المعلّقة
  يوقف كل الفحوص؛ أُصلح ليقرأ الاسم من جدول `users`، فعادت الإشعارات تعمل.
- **فشل مغلق لـ 2FA في الإنتاج:** الإقلاع يرفض العمل في `production` ما لم يُضبط
  `TOTP_ENC_KEY` (سابقاً كان يُشفّر بسر ثابت مكشوف في المصدر). التطوير/الاختبار
  يبقيان سلوك المفتاح الثابت للراحة.
- **حد أعلى لمبلغ شحن المحفظة اليدوي:** `assertAmount` يمنع إدخال مبالغ خيالية
  (سقف تريليون دينار).
- **CORS آمن:** أُضيف رأس `Vary: Origin`، وتفعّل `TRUST_PROXY` افتراضياً في الإنتاج
  كي تعمل حدود معدل الطلبات على عناوين IP الحقيقية خلف nginx.
- **تعقيم أوسع لحقن النموذج الأولي:** شمل `req.query` و`req.params` لا `req.body` فقط.
- **إيقاف رشيق وإقلاع آمن:** معالجة `SIGTERM`/`SIGINT` (إغلاق المستمع ثم الخروج)،
  التقاط `unhandledRejection`/`uncaughtException`، وتغليف إجراءات الإقلاع الأولية
  (الترحيل/التنظيف) بـ try/catch تفشل بوضوح بدل تعطيل الكتلة صامتاً.
- **إصلاح سكربت PM2:** `deploy/ecosystem.config.js` يشغّل `npm start` (عبر `tsx`)
  بدل ملف `src/index.js` غير الموجود، فلا ينكسر التشغيل عبر PM2.

### قيود معروفة عند التوسّع (للعلم لا للإصلاح العاجل)

- **حدود المعدل في الذاكرة لكل عملية:** ليست موزّعة؛ خلف عدة نسخ استخدم Redis أو
  اعتمد على قفل الحساب المبني على قاعدة البيانات (`lockout`) لحماية الدخول.
- **حظر حلقة الأحداث أثناء استعلام DB:** كل عملية DB متزامنة عبر العامل؛ تجنّب
  المعاملات الطويلة، ورفع `CLUSTER_WORKERS` عند الحاجة.
- **أموال بفاصلة عائمة:** تُدار عبر `round2` مع حدود `assertAmount`؛ التحويل إلى
  أعداد صحيحة (فلس) هو خطوة تحصين لاحقة موصى بها للمالية الحرجة.

## بدائل لا تتطلب سيرفرك الخاص

- يمكن نشر مجلدات `dist` على أي استضافة ساكنة (Netlify/Vercel) والخادم على
  (Render/Railway/Fly) مع HTTPS مدمج، وربط `/api` عبر عكس وكيل الاستضافة.
